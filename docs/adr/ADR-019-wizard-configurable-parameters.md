# ADR-019：安装向导与应用设置统一收口六个运行参数

## 状态

已接受，2026-11-24 起生效，对应发布版本 `0.2.4`。已在 fnOS 测试机（192.168.5.141，
x86_64）完成安装、应用设置、密钥轮换与非法输入拒绝的实机验收。

## 背景

ADR-006 已声明「端口通过安装向导和应用设置修改」，但落地时只做到一半：

- `wizard/install` 只有 RPC 端口与 BT 监听端口两项；
- `wizard/config`（应用中心「应用设置」）完全不存在，`cmd/config_init` 与
  `cmd/config_callback` 是空壳脚本，直接 `exit 0`；
- DHT 监听端口、RPC 密钥、归档模式（`SPECIAL_MODE`）、下载文件夹路径只能在
  `config.json` 里手工改，普通用户没有入口；
- RPC 密钥由安装脚本随机生成 48 位后即固定，用户无法更换。

用户要求这六项在安装时能设置，安装完成后也能在应用设置里修改，并且重启后生效。

## 决策

1. **六个字段统一走飞牛向导机制。** 字段名固定为 `wizard_rpc_port`、
   `wizard_listen_port`、`wizard_dht_listen_port`、`wizard_rpc_secret`、
   `wizard_special_mode`、`wizard_download_root`。`wizard/install` 与
   `wizard/config` 共用同一字段名：向导值以环境变量注入生命周期脚本，改名会让
   已发布版本的用户输入失效。

2. **落盘逻辑收口到 `aria2-manager --apply-wizard`。** 端口校验、端口互斥、密钥
   字符集、下载目录是否位于飞牛共享目录、归档目录派生与属主继承，全部复用常规
   配置路径的同一份代码。生命周期脚本只做三件事：`*_init` 预先校验（安装阶段
   二进制尚未落地，无法调用管理器），`*_callback` 调用管理器落盘，`config_callback`
   在服务运行时执行一次受控重启。

3. **空值语义是“不修改”。** `wizard/config` 中端口、密钥、下载目录的 `initValue`
   为空，归档模式提供「保持当前设置」选项。这样无论飞牛是否回填上次提交值，保存
   设置都不会把用户没有触碰的字段重置为出厂值；安装流程的空值则回落到出厂默认，
   密钥为空时自动生成随机值，保证新装不需要用户理解 RPC 密钥也能用。

4. **RPC 密钥下限由 32 位放宽到 16 位，并限制字符集。**（此条已被决策 9 取代：
   下限进一步放宽到 8 位、字符集放宽到可见 ASCII。）
   允许 `[A-Za-z0-9._-]`：`aria2.conf` 由 shell 逐行写出，含空白、引号、反斜杠或
   `#` 的取值会截断行或注入额外选项，因此在入口处拒绝。密钥先校验后落盘，避免
   留下「配置已改、重启后连不上」的中间态。

5. **下载目录的可用范围是“飞牛数据卷 + 应用用户可写”。** 原实现只接受随包声明的
   `data-share` 与 `config.json` 里的 `authorized_roots`，导致用户在应用设置里填
   `/vol1/1000/downloads` 这类已有共享目录时保存失败（实机复现为 `15002: exit code 1`）。
   改为两级判定：已授权根内直接通过；根外的路径只要落在 `/vol<N>/` 下，并且以专属应用
   用户身份实测可写，就允许。系统目录（`/etc` 等）与临时目录仍然拒绝。
   `TRIM_DATA_ACCESSIBLE_PATHS`（飞牛在应用设置里逐项授权的目录）一并纳入已授权根。

   判定必须实测写入而不是看权限位：fnOS 的数据卷以 `trimacl` 挂载，`getfacl` 看不到
   实际授予结果，而安装/配置回调以 root 运行，直接 `CreateTemp` 恒成功。实现里在
   root 上下文用 `setpriv --init-groups` 降权到应用用户后创建测试文件，避免把 aria2
   实际写不进去的目录当成可用。启动自愈使用同一判定，否则用户设置的目录会在下次启动
   被静默改回默认值。

6. **任务清理范围随下载目录派生，不引入第二处配置。** 「删除任务」与「清空已结束任务」
   在 AriaNg 里都是先调 `/api/v1/cleanup` 删文件、成功后才移除任务记录，因此清理接口
   一旦拒绝，两个功能就整体失效。清理范围（`taskScope`）必须包含当前的下载目录与归档
   目录，否则用户把下载目录改到共享目录之外以后，删除任务会因“越界”全部失败。

   由此确定产品口径：**只暴露一个“下载文件夹路径”设置**。内部允许范围由它派生
   （下载目录 + 归档目录 + 应用共享目录 + 飞牛授权目录），不需要用户再维护一份
   “可访问文件夹”清单——两份配置必然会出现不一致，这次故障就是不一致的表现。

7. **RPC 密钥字段使用 `text` 而不是 `password`。** 设备实测：飞牛的应用设置表单在
   `type: "password"` 时**不会提交用户的编辑值**——输入框里已经是新密钥，但保存请求
   携带的仍是页面加载时的旧值（同一表单里 `text` 类型的端口改动可以正常提交）。
   结果是密钥永远改不掉，而按钮仍会触发一次重启，用户看到的是“保存成功 + 服务异常、
   密钥没变”。改为 `text` 后实测提交值正确、`rpc.secret` 与 `aria2.conf` 同步更新。

   代价是密钥在设置页以明文显示。权衡：`GET /v1/config/wizard` 本来就以明文返回该
   值，页面只有管理员可见，因此没有扩大暴露面；换取“密钥可修改”这一功能是值得的。
   安装向导的同一字段一并改为 `text`，避免安装期填写的密钥被静默丢弃。

8. **文件夹选择器放在应用内，不放在安装向导里。** 飞牛向导只支持
   `text`/`password`/`radio`/`checkbox`/`select`/`switch`/`tips` 七种字段，没有目录选择
   控件（设备实测：自定义 `directory` 类型只渲染出标签，没有输入框）。因此下载目录在
   安装向导与应用设置里都是文本框，并在向导里用 `tips` 指向真正的选择入口。

   真正的选择器是应用已有的 Aria2 右上角文件夹菜单 →「选择并授权目录」
   （`fpk/app/www/fnos-directory-adapter.js` → `pickUserFile({directory:true})`）。它一次
   完成两件事：由飞牛 SDK 授权该目录（登记进应用授权，`TRIM_DATA_ACCESSIBLE_PATHS`
   里可见，即应用中心「可访问的文件」），并把路径写入 `config.json` 的 `download_root`
   （即应用设置「运行设置」）。管理器同时把该路径加入 `authorized_roots`。

9. **RPC 密钥只拒绝“会破坏配置行”的字符，其余一律接受。** 早先把密钥限死在
   `[A-Za-z0-9._-]{16,64}`，理由是“aria2.conf 由 shell 写出，特殊字符会截断行”。
   复核 aria2 的配置解析（`src/OptionParser.cc`：按第一个 `=` 切分、取值原样保留到行尾、
   只有行首 `#` 是注释、不做引号与转义处理）后可以确认这个理由只对**换行**成立：
   符号（`@ ! # $ ' " \`）都是普通字符。过严的规则带来的是实打实的故障——用户填
   `Vinson@2024`、`vinson520` 这类常见口令时保存失败，而应用中心的配置流程只回
   `15002: exit code: 1`，界面上表现为“保存成功 + 服务异常”，完全看不出是密钥不合规。

   现在的规则：8-128 位、可见 ASCII（`0x21-0x7E`，即不含空格、制表符与换行）。空白与
   换行仍然拒绝（换行会插入新配置项，空白会让值带上不可见差异），非 ASCII 也拒绝
   （中文/全角符号容易被复制成“看起来一样”的不同字节）。Go 与三处 shell 脚本使用
   同一套判定。

   同时给这个字段加了前端 `rules.pattern`：不合规时字段变红并在下方给出原因，点保存
   不会发出任何请求。这样即使将来判定再收紧，用户也能当场看到原因，而不是事后面对
   一个通用错误码。

   可写范围放宽不代表放弃安全边界：RPC 只监听 `127.0.0.1`，外部访问必须先过飞牛网关
   鉴权，密钥是网关之后的第二道门槛；8 位可见字符足以支撑这个定位。

10. **用户填的已有目录由应用自动完成授权，不要求用户先去点选择器。** 安装向导没有
   目录选择器（决策 8），用户只能手填路径；而手填的目录通常是管理员自建的共享目录
   （属主 `admin`、权限 755），飞牛又没把这个路径授权给本应用，于是专属应用用户写不
   进去，实机表现为安装中止在写探测处（`cannot touch ... Permission denied`）。

   设备上实测了三种授权方式的差异：

   | 方式 | 结果 |
   |---|---|
   | `setfacl -m u:aria2:rwx` / `g:AppUsers:rwx` | **无效**（trimacl 不认 POSIX ACL） |
   | `chmod 777` | 可写，但等于对所有人开放 |
   | `chgrp aria2` + `chmod g+rwx`（属主不变） | **可写，且只有本应用的专属组能写** |

   因此采用第三种：`ensureAppWritable` 先降权实测，失败就把目录的组改为飞牛注入的
   `TRIM_GID`（与应用同名的专属组，成员只有该应用用户）并补组写权限，属主与 other
   位保持不变。用户自己在文件管理器里看到的属主不变，普通用户也仍然可写。

   这条只作用于用户显式选择的下载目录与其派生的 `completed`；系统目录、数据卷以外的
   路径依然拒绝（`downloadRootAllowed`）。新建目录仍按原逻辑直接归属应用用户。

11. **组授权不是持久状态，必须运行期看护。** 决策 10 用 `chgrp 专属组 + 组写权限`
   让 aria2 能写用户自选的目录，但飞牛会在**开机**（以及部分共享目录操作后）重新
   应用共享目录权限，把组改回管理员——这不是我们的写操作失效，而是权限归属不在
   飞牛的模型里。

   实测确认两点：
   - 目录组为 `aria2` + 775 时 aria2 可写；改回 `Administrators` + 755 后立刻
     `Permission denied`，与是否登记在「可访问的文件」无关（子目录也不会继承授权）；
   - 因此只靠启动时补一次授权，会留下整段不可写的时间窗：开机后应用启动早于或晚于
     权限服务都会中招，用户看到的是「应用设置里的授权文件夹失败、下载全部失败」。

   处理办法：`cmd/main` 在启动完成后拉起一个看护循环（root 身份），调用
   `aria2-manager --repair-permissions`；该子命令只在实测不可写时重新授权并输出一行，
   看护把该行写进 `startup.log`（`运行期权限自愈：...`）。看护进程随管理器退出而结束，
   不新增常驻服务。

   周期：单次检查实测约 10 毫秒，因此固定 **15 秒一次**——既覆盖开机后权限服务晚于
   应用执行的竞争窗口，也覆盖用户在文件管理器里手动改权限。实测重置权限后恢复耗时为
   8 / 12 秒。启动流程本身先修权限再拉起 aria2c，所以「应用启动」这一步没有窗口；
   需要兜的是应用已在运行时权限被外部改回的情况。

   这条也解释了为什么“同一台机器有时开机正常、有时失败”：取决于飞牛权限服务的执行
   时机与应用启动的相对顺序，以及目录此前是否被手工改过。

12. **下载目录允许尚不存在。** 逐级创建，新建目录直接归属专属应用用户（而不是沿用上级
   目录属主——`/vol1/1000` 属于管理员，沿用会导致 aria2 无法写入）。归档目录仍按
   ADR-018 恒定为 `<下载目录>/completed`，不新增配置项。

## 后果

- 六个参数在安装期与运行期各有一个入口，任何一个入口的校验规则必须与
  `aria2-manager --apply-wizard` 保持一致；`*_init` 里的 shell 校验是同一口径的
  提前反馈，不是第二套规则。
- **`config_callback` 不自行重启应用。** 应用设置弹窗的按钮是「保存并重启」，配置流程
  返回后由应用中心调用 `POST /v1/restart` 完成重启。回调里再重启一次会与它撞车
  （App Center 侧 stop/start 状态冲突），实机表现为先提示「保存成功」、紧接着提示
  「服务异常」。因此回调只负责落盘与属主恢复，重启交给应用中心。端口、密钥、下载目录
  都在这次重启中由 `cmd/main` 重新生成 `aria2.conf` 后生效；如果绕过界面直接调
  `POST /v1/config/wizard`，改动会在下一次重启时生效。
- 该放宽改变了 ADR-007 中“下载目录必须位于已授权共享目录”的口径：授权来源扩展为
  “飞牛数据卷 + 实测可写”。安全边界仍在：应用用户写不进去的路径、以及数据卷以外的
  系统路径一律拒绝。
- `aria2-manager --apply-wizard` 在配置与密钥都没有变化时以退出码 `2` 结束，
  `config_callback` 据此跳过重启：用户在设置页原样保存一次不应打断正在进行的下载。
- 清理接口对单个路径失败改为“跳过并记日志”后，越界或不可删的文件会留在磁盘上，
  但任务记录可以正常删除。日志写入 `$TRIM_PKGVAR/manager.log`，便于事后追查。
- 启动期 `--ensure-ports` 仍会在端口被占用时自动改端口并回写配置。用户手填的端口
  不是硬约束，而是首选值。
- 该机制依赖飞牛 `GET/POST /v1/config/wizard` 把 `wizard/config` 渲染到应用设置页。
  设备实测确认：**飞牛会把当前值回填进 `initValue`**（含 RPC 密钥，以密码框回显），
  因此正常路径下用户看到的就是现值，“空值 = 不修改”只在回填缺失时兜底。
- 因为表单会连密钥一起回填并再次提交，“提交了密钥”不能等同于“密钥变了”。实现里
  会比对密钥文件内容，内容相同即视为无变化，否则一次原样保存就会触发重启。
- 配置流程失败时飞牛只返回 `15002:exit code: 1`，不展示 `TRIM_TEMP_LOGFILE` 的中文
  原因（安装流程会展示）。维护者需要知道这一点：用户在设置页看到的是通用错误码，
  真实原因在 `$TRIM_PKGVAR/startup.log` 与脚本 stderr。
