# 需求分析

## 功能需求

### 原生 FPK 应用

- 依照飞牛 FPK 生命周期完成安装、启动、停止、状态查询、升级、配置和卸载。
- 运行时不依赖 Docker，也不引入应用级数据库。
- 使用专属飞牛应用用户和满足需求的最小权限。

### Aria2 Pro 服务

- 运行固定版本的原生 Aria2 Pro Core。
- 正常重启后恢复下载任务，保留进行中的下载进度。
- 持久化 Aria2 会话及 IPv4/IPv6 DHT 状态。
- 支持 HTTP(S)、FTP、BitTorrent、磁力链接、Metalink 和 RPC 控制。
- 支持配置 BT/DHT 监听端口、磁盘缓存、IPv6、umask 及稳健的连接/重试参数。
- RPC 端口和 BT/DHT 监听端口可修改，默认分别为 `6800` 和 `6888`；两者必须支持独立配置。
- 端口值必须校验为合法用户态端口，拒绝与系统已占用端口冲突；配置修改后应提示需要重启服务，并验证新端口已监听。
- 无需重启活动下载即可更新公共 BT Tracker。
- 支持失败/删除任务与完成控制文件的清理策略。

### 飞牛 Web 体验

- 通过统一网关在飞牛桌面 iframe 内打开。
- 使用 AriaNg，但不暴露 Aria2 RPC 密钥。
- 第一版仅允许管理员控制服务。
- 在目录选择、目录授权、文件管理器跳转、设置跳转、主题和语言适配等场景使用飞牛 Web SDK。

### 配置

- 安装时生成 RPC 密钥。
- 升级时保留用户配置。
- 为支持的选项提供应用配置页面。
- 每个配置值都必须在写入 Aria2 配置文件前校验。

## 重要风险

- **原生二进制兼容性：** Aria2 Pro Core 必须可复现构建并按 CPU 架构打包；动态依赖可能随 fnOS 版本变化失效。
- **文件系统授权：** 应用用户不能安全地假设可访问任意用户目录，下载目标必须有明确的飞牛权限策略。
- **破坏性清理：** 原始 P3TERX 回调会在错误或删除任务后删除文件，必须限制在已验证任务路径内，并提供安全默认值。
- **Tracker 供应链：** 不能运行时下载脚本或配置；Tracker URL 需要验证、网络超时限制和失败降级。
- **PT 使用：** PT 站点可能禁止 Aria2 或客户端伪装；PT 预设不得默认启用，并需明确用户确认。
- **共享守护进程：** 单个 Aria2 实例拥有全局会话、全局配置与端口，第一版应仅管理员使用；多用户隔离需另行设计。
- **端口变更：** 修改 RPC 或 BT/DHT 端口会中断对应服务，必须采用暂停任务、写入配置、受控重启、监听验证和失败回滚的流程。

## 第一版非目标

- 重写 AriaNg。
- 要求 NAS 安装 Docker、数据库服务或解释型语言运行时。
- 提供公网 RPC。
- 自动下载、安装或更新 Rclone。
- 不受限制地访问所有飞牛用户路径。
