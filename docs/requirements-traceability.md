## 质量门槛

### Phase 1 退出门槛（历史门槛记录）

- 产品目标、用户模型、非目标和安全基线已记录。
- 技术栈、组件边界、目录职责和端口策略已记录。
- 关键架构决策均有 ADR。
- 发布前决策项已明确列出，未确认项不被假定为已批准。
- 在阶段一未完成前不创建任何 Phase 2 的 FPK 源目录或业务实现；该门槛已在五项
  决策确认后通过，当前仓库已进入 Phase 2。

### 进入 Phase 2 的必要条件

只有在用户确认应用标识、首发架构、下载目录策略、首版归档范围和更新分发方式后，才允许创建 `fpk/` 骨架。若这些决策发生变化，应先更新 `PROJECT_CONTEXT.md` 和相关 ADR。

## 测试证据规则

- 文档检查只能证明设计记录存在，不能替代运行时测试。
- fnpack 成功只能证明包格式有效，不能证明服务行为正确。
- 测试机验证必须记录系统版本、应用版本、架构、配置和关键日志摘要。
- 涉及删除文件、端口切换或升级的测试必须使用专门测试目录和可恢复数据。
- UI 验证必须检查浏览器存储、静态资源和网络请求，证明 AriaNg 未暴露远程 RPC、
  自定义 Header 或 RPC secret 配置入口。
- 若实际分发飞牛 Web SDK，测试与发布记录必须包含其版本、许可和传递依赖审查结果。
