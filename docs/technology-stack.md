# 技术栈设计

## 选型总览

| 层次 | 选型 | 选择理由 |
| --- | --- | --- |
| 应用打包 | fnOS FPK、`fnpack 1.2.3` | 使用飞牛原生安装、升级、权限、资源和生命周期能力 |
| 下载核心 | Aria2 Pro Core 原生二进制 | 保留增强版 aria2 的下载、BT、DHT、恢复和回调能力 |
| 管理服务 | 静态链接 Go | 适合常驻 Unix Socket 服务，启动快、部署单文件、无需 NAS 运行时 |
| Web 界面 | 固定版本 AriaNg | 使用成熟的 Aria2 Web 控制界面，避免重复实现任务管理 |
| 飞牛适配 | `@trimjs/web-app@0.4.2` | 目录选择/授权、文件管理器、应用设置、主题和语言等宿主能力 |
| 网关通信 | fnOS 统一网关 + Unix Socket | 复用飞牛登录态，支持常驻服务和后续 WebSocket 扩展 |
| 本地 RPC | Aria2 HTTP JSON-RPC | 管理器代理到回环地址，浏览器不接触密钥 |
| 配置存储 | 文本配置与 JSON 元数据 | 单实例首版数据模型简单，不引入数据库维护成本 |
| 测试 | Go 单元测试、Shell 静态检查、fnpack 校验、测试机验收 | 覆盖逻辑、打包和真实 fnOS 生命周期 |
| 构建 | 固定源码修订、校验和、交叉编译 | 保障可复现和架构隔离 |

## 运行时依赖原则

首版 FPK 不依赖 NAS 上预装的 Node.js、Python、Java、Docker 或数据库。AriaNg
和 SDK 在开发机完成构建，最终只将静态资源打入 FPK；Go 管理器和 Aria2 Core
也以目标架构二进制随包发布。

## 为什么不使用 Node.js

Node.js 可以快速实现 HTTP 服务，但会把一个额外的运行时、版本兼容和安全更新
责任带入 NAS。当前服务只需要静态文件、有限的 HTTP 代理、配置读取和调度，静态
Go 二进制更符合 FPK 的自包含目标。若未来需要复杂的前端服务端渲染或插件系统，
再单独评估 Node.js 依赖。

## 为什么不直接使用 CGI

CGI 适合简单静态页面，但每次请求都启动进程，不适合作为 Aria2 RPC 代理、长连接
入口和 Tracker 调度器。统一网关本身也明确区分了 CGI 与常驻 Unix Socket 服务。

## 前端边界

- AriaNg 只负责任务列表、任务操作和 Aria2 选项界面。
- 飞牛适配层负责宿主交互，不修改 AriaNg 的核心任务模型。
- UI 使用相对网关路径，不写死 NAS 地址、RPC 端口或 secret。
- 当前技术方案不承诺 AriaNg 原生 WebSocket；先使用管理器提供的 HTTP JSON-RPC
  代理，未来如有必要再通过同一网关前缀扩展 WebSocket。

## 安全与维护边界

- Go 管理器不得成为任意 URL 反代；后端目标只能是本地 aria2。
- 配置更新必须经过结构化校验，不能依赖不安全的字符串替换。
- Tracker 列表属于外部数据，不能作为脚本执行；更新失败不应停止下载服务。
- 所有上游源码、构建参数、版本和许可证在发布元数据中固定。
